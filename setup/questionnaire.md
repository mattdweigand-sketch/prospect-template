# Guided setup interview

Read supplied documents first. Extract candidate answers with source references and mark uncertainty. Ask only what is missing, inconsistent or consequential, in small batches. Do not make the user fill configuration files or invent persona/claim identifiers. Preserve unrelated settings when updating an existing install.

| Topic | Establish |
|---|---|
| Business and offer | Business name, product or service, what it does, who benefits, boundaries and unsupported promises |
| ICP | Buying entity, employee range, industries, territory exclusions, disqualifiers, recurring buyer work |
| Responsibility | Initiative owners, users, functional sponsors and evidence of responsibility; titles are search hints |
| Signals | Actions that suggest timely fit; source locations and example searches; clear/indirect/poor fit; freshness and qualification definitions |
| Messaging support | Exact supported assertions, source quotations, attribution, claim limits and permission to name customers; user statements remain attributed statements |
| Voice | One approved email sample or a newly approved sample recorded as a user statement; preserve the exact source text |
| Identity and operations | Seller email, CRM User Id, time zone, internal domains, house owners, native Task status mapping, suppression windows and reviewed fixed templates |
| Modules | Public prospecting by default; adoption discovery, account adoption and ARR enabled only if the business has the necessary model and reviewed warehouse access |
| Providers | Actual available tool names, input/output fields, pagination/completion, native readback; missing tools stay explicitly missing |
| Source and retention | Existing Git source at a full commit, or permitted local snapshots of supplied original bytes; redaction, local retention, backup and who can access them |
| Review | Messaging review date; explicit meaning review of all seven configuration files, source limits and three synthetic fit previews |

For a service business, describe deliverables and buyer work without inventing subscriptions, software capabilities or adoption data. Define signals and responsibilities from that service and the buyer's work. Do not import software assumptions. Keep specialized modules disabled.

Show a clear-fit draft, an indirect-fit case needing research, and a poor-fit rejection. Explain why each decision follows from the offer and evidence. Do not convert enthusiasm or a senior title into buying intent. Mechanical source matching is separate from this meaning review.

## CRM and email choices

Ask which CRM and email providers the user uses, which native tools are available, and how their account/company, contact/person, owner, deal, task/activity and event models relate. Confirm opaque owner IDs, active owner evidence, open-deal and task status meanings, account/contact associations, date/time representations, pagination and supported write/readback operations. For email, verify complete recipients/body, sent-state evidence, and draft versus message retrieval identifiers; thread support is optional. Populate `systems`, capability descriptions and record mappings in providers.yaml from those schemas. Exercise authorized reads or synthetic samples; a mapping test is not proof of live permissions. Leave missing capabilities null and report affected workflow branches.
